🌳 "checksum-real-world-testing"
📝 Comprehensive real-world testing of checksum-based concurrency detection using two separate MCP instances (test-memory-A and test-memory-B) that share the same memory root directory. Tests will validate all scenarios described in CHECKSUM-CONCURRENCY-DESIGN.md.
📊 ██████████ 100% (9/9 tasks)

├── ✅ |Sequential Modification Detection| "Test the main benefit: detecting modifications that occur BETWEEN separate operations (not during lock wait)\n\nScenarios:\n1. A reads file → B modifies → A writes (based on stale data) → Error expected\n2. A views full file → B str_replace → A str_replace (expecting old text) → Error with current content shown\n3. A views with range (not cached) → B modifies → A writes → Should NOT error (partial read not cached)" (🚨)
├── ✅ |Successful Operations| "Verify operations succeed when content matches expectations\n\nScenarios:\n1. A reads file → A immediately modifies → Success (checksum matches cache)\n2. A reads file → B does nothing → A modifies → Success\n3. A creates file → A modifies immediately → Success (checksum cached on create)\n4. Fresh operation with no cache → Success (no cached checksum to compare)" (🔴)
├── ✅ |Error Message Quality| "Verify error messages show current file contents when concurrent modification detected\n\nValidate:\n1. Error message includes 'File has been modified by another process'\n2. Current content is shown (truncated if >5000 chars)\n3. Truncation indicator present for large files\n4. Error message is actionable (tells user to re-read and retry)" (🔴)
├── ✅ |File Deletion Scenarios| "Test cache behavior when files are deleted\n\nScenarios:\n1. A reads file → B deletes file → A writes → Appropriate error (ENOENT, not checksum error)\n2. A reads file → A deletes file → Cache cleared\n3. A deletes file → B tries to access → File not found" (🟡)
├── ✅ |Rename Operations| "Test cache invalidation on rename\n\nScenarios:\n1. A reads /memories/old.txt → B renames to /memories/new.txt → A writes to old path → File not found\n2. A reads /memories/old.txt → A renames to /memories/new.txt → Cache cleared for old path\n3. A renames file → B reads new path → No cache (fresh read)" (🟡)
├── ✅ |Multiple File Operations| "Test checksum caching across multiple files\n\nScenarios:\n1. A reads file1 and file2 → B modifies file1 → A writes to file1 (error) and file2 (success)\n2. Cache isolation: Operations on different files don't interfere\n3. Cache per-path: Same filename in different directories treated separately" (🟡)
├── ✅ |Large File Handling| "Test content preview truncation for large files\n\nScenarios:\n1. Create file >5000 chars → B modifies → A writes → Error message truncates content with indicator\n2. Verify hash computation time acceptable for typical files (<50KB)\n3. Edge case: Very large file (1MB+) - still works, just slower" (🔵)
├── ✅ |Directory Operations| "Verify directories are NOT checksummed\n\nScenarios:\n1. A views directory → No cache created\n2. B adds file to directory → A views directory again → Success (directories not cached)\n3. Operations on files within directories work normally" (🔵)
└── ✅ |Edge Cases| "Test boundary conditions and unusual scenarios\n\nScenarios:\n1. Empty file handling (checksum of empty string)\n2. File with only whitespace/newlines\n3. Unicode content (ensure UTF-8 encoding consistent)\n4. Rapid sequential operations (A reads, A writes, A writes again)\n5. Same content, different operations (str_replace vs insert vs create)" (🔵)
